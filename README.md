# Планировщик городского досуга для MAX

Основной сценарий: сообщение боту MAX → Alice Flash → короткие уточнения кнопками/геолокацией в чате → 2ГИС Places/Routing → Python/OR-Tools → план в чате. Mini-app показывает подробную ленту, карту при наличии отдельного ключа и позволяет править условия. Оба интерфейса используют одно состояние в PostgreSQL; учебные места не подставляются. Перед включением webhook нужны выкладка и живой проход через MAX.

## Запуск приложения

1. Установите Docker Desktop с Compose.
2. Выполните `npm.cmd run env:init` и заполните `.env.local` по `.env.example`: MAX, Yandex, 2ГИС и отдельный `POSTGRES_PASSWORD`. Для пароля Compose используйте случайную строку из букв/цифр (другие символы требуют URL-кодирования в DATABASE_URL).
3. Из корня продукта запустите:

```powershell
docker compose --env-file .env.local up --build -d
```

Compose запускает приложение и PostgreSQL. Локальный адрес: http://127.0.0.1:3000. Вне MAX вход в планировщик закрыт, учебная авторизация в рабочем сервере отсутствует. Для реального запуска из MAX разместите контейнер по HTTPS, подключите постоянную базу в РФ, задайте ссылку mini-app у бота и настройте webhook после выкладки.

Остановка: `docker compose --env-file .env.local down`. Том базы остаётся; `down -v` удалит данные, не используйте его для обычной остановки.

Для разработки без пересборки Docker: установите Node-зависимости (`npm.cmd ci`), Python по [planner/README.md](planner/README.md), укажите `DATABASE_URL` доступной PostgreSQL и выполните `npm.cmd run dev`. Фронтенд — 5173, API — 3000.

## Пользовательский сценарий

- При первом запуске MAX показывает свою кнопку «Начать»; событие запуска даёт боту возможность отправить приветствие и кнопки. Для уже открытого чата доступны `/start` и меню под сообщениями. Штатную кнопку до первого сообщения нельзя создать средствами нашего сервера.
- «Новый маршрут», «Мои маршруты», «Выйти из планирования» и команды `/new`, `/routes`, `/exit`, `/menu` управляют режимом чата. Под сообщением видны только действия, уместные на текущем этапе: вне планирования нет кнопки выхода, при ожидании нового пожелания нет повторной кнопки создания, при уточнении первыми идут варианты ответа. Старые inline-кнопки остаются в истории MAX, но сервер проверяет активный маршрут при нажатии. В открытом маршруте случайный свободный текст не начинает другой план. В списке можно выбрать ранее созданный маршрут или удалить его с подтверждением.
- Написать боту обычными словами, чем и когда хочется заняться. Если город неясен, бот спросит его один раз; неизвестный город не заменяется Москвой.
- Сервер получает каталог выбранного региона и делает один запрос Alice Flash. «Погулять» без иного транспорта предлагает пеший режим.
- Бот показывает «Я правильно понял?» и только первый необходимый вопрос. Старт задаётся кнопкой геолокации, выбором точки на карте (при доступном MapGL) или вводом адреса с выбором найденного дома; уже распознанные условия не приходится заполнять повторно.
- Подтвердить условия кнопкой и получить план с местами, временем посещения, дорогой и примерными расходами прямо в чате.
- При желании открыть mini-app для подробной ленты, карты и правок выбранного в чате маршрута. Изменения полей и навигация не вызывают LLM.

Линия маршрута на карте пока не отображается: матрица времени не является геометрией пути. PT/смешанные режимы, билетные события, сохранение в избранное и отправка плана ещё не подключены. Длительности посещений — явно заданная политика для поддержанных рубрик; неизвестные длительности/часы/цены не выдумываются. Строгий бюджет может исключить места, для которых известен только средний чек без надёжной верхней границы.

## Постоянное состояние и ограничения

PostgreSQL хранит черновики, версии, счётчики обращений и квитанции действий для нескольких экземпляров сервера. TTL состояния планировщика — 30 минут, выдачи результата — 5 минут. Отдельный список пользовательских маршрутов без фиксированного ограничения по количеству хранится 30 дней после последнего изменения: в нём есть исходный текст пожелания, название города и ID краткоживущего черновика, но нет сохранённых карточек/маршрутов 2ГИС. Пользователь может удалить запись в чате; доступный черновик также удаляется. Если черновик истёк, его обновление — явное действие с новым обращением к географии/LLM и свежей проверкой мест. Очистка просроченного состояния — при запуске и раз в минуту. Это **не постоянный каталог или reusable provider cache**; нормализованный результат всё же входит в краткоживущее состояние сеанса. До публикации подтвердите допустимость такого хранения и retention. В квитанции остаётся хеш исходного текста, но в списке маршрутов текст хранится для явного восстановления. Черновик содержит извлечённые пожелания и координаты.

Миграция `src/server/planning-schema.sql` добавляет только таблицы/индексы, выполняется при старте под advisory lock. Нужна прямая PostgreSQL-сессия или session pooling; transaction-mode PgBouncer не поддерживается. Для отката приложения таблицы не удалять. `DATABASE_CA_PATH` включает проверяемый TLS с CA — не отключайте проверку сертификата.

Повтор event_id не повторяет оплаченный запрос; после обрыва с неизвестным исходом требуется новое явное действие. Суточных и поминутных квот на количество запросов, расчётов и поисков нет; таблица суточного использования остаётся только для учёта. Сохраняются ограничения размера входных данных, таймауты, предотвращение одновременных дублей и два одновременных разбора/расчёта на базу. При создании нового маршрута каталог категорий запрашивается один раз: используется вложенное дерево полной корневой страницы, без дополнительных запросов по каждой родительской категории и без кэша между запросами. Если дерево неполно или недоступно, маршрут не создаётся. Это не независимая сверка всех дочерних списков; она остаётся отдельной процедурой offline-оценки. При явном ответе 2ГИС об исчерпании лимита конкретного сервиса сервер один раз переключается на резервный ключ; остальные сервисы остаются на основном. Резерв не помогает, если оба ключа относятся к подписке с общим исчерпанным лимитом. Неизвестные ошибки, таймауты и неверные параметры не вызывают смену ключа. Без внутренних квот платные обращения могут увеличить расходы: контролируйте счёт и бюджет в Yandex Cloud и 2ГИС.

Основной entry point регистрирует `GET /api/planning/bootstrap`, `GET /api/planning/localities?q=...`, `POST /api/planning/requests`, `GET/PATCH /api/planning/drafts/:id`, `POST /confirm`, `POST /plan`. Все требуют `X-Max-Init-Data: <подписанный initData>`. Yandex Serverless Containers удаляет входящий `Authorization`, поэтому его нельзя использовать для передачи данных запуска. Без необходимых переменных bootstrap возвращает 503, без валидной подписи — 401; фиктивного fallback нет.

### Адаптер Alice Flash

`src/server/intent-start.ts` переносит проверенное первоначальное извлечение в продукт; runtime не зависит от соседнего служебного каталога. Prompt v0.8, JSON-schema v0.2, postprocessing и серверные предложения времени лежат в `src/server/intent/`; ресурсы копируются в серверную сборку. Общий бюджет, ограничения и порядок не делятся и не теряются. Неопределённые единицы бюджета остаются `unknown`, блокируют подтверждение и выбираются в форме.
При ошибках `CATEGORY_ID`/`NONCONTIGUOUS_OFFSETS` разбор допускает ровно один дополнительный платный вызов Alice с проверенными ID конкретных дочерних рубрик; оба вызова отражаются в счётчике использования. Невалидный ответ не превращается в план автоматически.

`YandexIntentClient` — серверный транспорт Alice Flash: фиксированный официальный endpoint, structured output, 30 секунд, максимум 4096 выходных токенов, `store:false` и `x-data-logging-enabled:false`, без retries и смены модели. При создании обязательно задаются ключ, folderId, `maxCalls`, `maxEstimatedRub`; ключ не входит в браузерный ответ. Оценочный резерв на каждую попытку — 7,3728 ₽ по проверенному 24.09.2026 тарифу, без возврата резерва после ошибок. Это локальный ограничитель по зафиксированному тарифу, **не гарантия списания**; отдельный облачный бюджет и актуальность тарифа нужны при реальном запуске.

Адаптер подключён к рабочему серверу. Сквозной сценарий в MAX проверен для маршрута питания; прогулка с неподтверждёнными часами работы выдаётся только как предварительный план с явным предупреждением. Unit/integration tests подменяют только внешние provider-ответы. В продукт не копировались закрытые каталоги/чужие данные. Полный региональный каталог передаётся адаптеру сервером; два типа в offline fixture — только учебные данные, не фильтр реального продукта.

## Требования к окружению

- Node.js `24.15.0` (закреплён в `.nvmrc`; минимально `22.15.0`);
- npm из поставки Node.js;
- Docker с Compose — для контейнерного запуска.

## Первый локальный запуск

```shell
npm ci
npm run env:init
npm run dev
```

После `npm run env:init` заполните все переменные рабочего сценария (MAX/Yandex/2ГИС/DATABASE_URL), подготовьте PostgreSQL и Python, как описано выше. Клиент — `http://127.0.0.1:5173`; API — `http://127.0.0.1:3000`, проксируется Vite. Вне MAX защищённый сценарий не открывается.

`.env.local` игнорируется Git. В репозитории хранится только `.env.example`; реальные секреты передаются команде через защищённый канал и задаются в secret store хостинга/CI. Никогда не добавляйте серверный токен в переменные с префиксом `VITE_`.

## Запуск в Docker

Сначала один раз создайте `.env.local`, затем:

```shell
npm run env:init
docker compose --env-file .env.local up --build
```

Приложение откроется на `http://127.0.0.1:3000`: Compose публикует внутренний порт контейнера `8080` на локальном порту `3000`. Compose запускает контейнер с read-only filesystem, непривилегированным пользователем и healthcheck. Остановка:

```shell
docker compose --env-file .env.local down
```

## API и граница доверия

- `GET /api/health` — process health endpoint, не проверка доступности внешних API;
- `GET /api/public-config` — только публичная конфигурация MapGL, без серверных ключей Places/ Routing;
- `POST /api/auth/max` — принимает только `{ "initData": "..." }`, проверяет подпись, `auth_date` и пользователя;
- `POST /api/max/webhook` — проверяет `X-Max-Bot-Api-Secret`, обрабатывает личные сообщения и callbacks бота;
- остальные GET-запросы с `Accept: text/html` возвращают SPA.

Frontend не доверяет `initDataUnsafe` и не получает `MAX_BOT_TOKEN`. В обычном браузере он просит открыть приложение из MAX; сервер проверяет подпись при каждом planning-запросе. Логи редактируют `X-Max-Init-Data`, `Authorization` и `initData`.

Диагностический экран MapGL открывается локально по `http://127.0.0.1:5173/?map=2gis-smoke`. Он не заменяет основной экран продукта. Один demo key можно временно повторить в трёх локальных переменных, но production в таком случае не отдаст MapGL-ключ браузеру: для развёртывания нужен отдельный ключ с ограничением по origin. 2ГИС разрешает создать бесплатный demo key только один раз; дополнительные ключи доступны в рамках подписки, поэтому наличие отдельного production-ключа нужно проверить в Platform Manager заранее. Сырые ответы Places/Routing используются только внутри расчёта; нормализованный пользовательский результат кратковременно сохраняется в PostgreSQL. Права на это хранение до публичного запуска проверяются отдельно.

## Ядро пользовательского запроса

- `src/shared/planner-domain.ts` содержит строгие Zod-контракты request-слоя версии `planner-domain.v0.1`;
- `src/server/intent-parser.ts` преобразует текст в `PlanningRequestDraft`, но не угадывает отсутствующие город, границы времени, точку старта или транспорт;
- parser-core использует только детерминированные правила. Его словарь интересов — стартовая ограниченная таксономия, а не универсальная NLP-модель;
- `selectNextClarificationQuestion` сохраняет порядок `BLOCKER → SAFETY → QUALITY`;
- `confirmPlanningRequestDraft` создаёт `PlanningRequest` только из состояния `READY_FOR_CONFIRMATION`.

Этот прежний детерминированный parser-core сохранён для тестов; рабочий первоначальный ввод использует Alice Flash и последующую строгую валидацию. Чатовый адаптер хранит шаг уточнения и квитанции событий в общем состоянии владельца; повтор доставленного события не должен повторять оплаченный разбор. Живой проход через MAX обязателен перед заявлением о готовности.

## Production и привязка к MAX

### Существующий Yandex Serverless Container и PostgreSQL на ВМ

Для облачного TLS передайте `DATABASE_URL` и публичный CA через `DATABASE_CA_PEM`
из Lockbox; альтернативно укажите `DATABASE_CA_PATH` внутри контейнера. Не задавайте
оба CA-параметра одновременно и не добавляйте SSL-параметры в строку подключения.
Production требует CA. Локальный Compose явно допускает plaintext только к своему
сервису `database`; исключение не переносить в облако.

`node scripts/configure-yandex-secrets.mjs` проверяет наличие необходимых локальных
настроек без сети. С `--apply` читает DATABASE_URL и публичный CA по SSH с уже
доверенного сервера, обновляет существующий Lockbox новой версией на основе прежней
(остальные поля сохраняются) и выдаёт существующему runtime SA payloadViewer только
на этот секрет. Подготовленные ключи берутся из `.env.local`; значения не печатаются
и не записываются во временные файлы. Закрытые TLS/SSH-ключи не передаются в Lockbox.
После успешного add-version сохраните показанный Version ID. При сбое после этой
операции проверьте версии перед повтором — создание новой версии не идемпотентно.
Подготовка **не** переключает ревизию приложения и не делает LLM-запросов. Новую
версию секрета при rollout следует закреплять явно, сохраняя все secret mappings.

После выкладки навигации можно выполнить `npm.cmd run max:commands -- --apply`:
скрипт сохранит существующие команды бота и добавит `/start`, `/new`, `/routes`,
`/exit`, `/menu`. Сначала запустите `npm.cmd run max:commands` без `--apply` и
проверьте список. Inline-кнопки в сообщениях работают и без регистрации команд.

После успешной подготовки Lockbox запустите из корня проекта
`npm.cmd run deploy:yandex:live` в PowerShell с работающими `yc` и Docker.
Скрипт проверит существующую ревизию и URL, соберёт и отправит образ в Container
Registry, выпустит новую ревизию **того же** Serverless Container с закреплённой
версией секрета, приватной VPC-сетью и проверяемым TLS к PostgreSQL, затем проверит
`/api/health`, закрытый `/api/planning/bootstrap` и публичную конфигурацию.
`PORT` не передаётся как переменная ревизии: Yandex Cloud запрещает её задавать;
в Docker-образе приложение уже слушает порт 8080.
При неудачной HTTP-проверке он попытается вернуть прежнюю ревизию. Скрипт не делает
платных запросов к LLM или 2ГИС. Проверка API не заменяет ручной проход по экрану
внутри MAX. Если версия Lockbox после подготовки изменилась, сначала проверьте её:
скрипт намеренно остановится, не выбирая секреты по умолчанию.
Если образ уже загружен, но команда создания ревизии завершилась ошибкой, запустите
`node scripts/deploy-yandex-live.mjs --apply --reuse-image-tag=<ранее загруженный тег>`:
это пропустит повторную сборку и загрузку. При отказе CLI выводится одна
укороченная строка причины с маскированием URL БД, токенов и ключей.

Резервные копии вне ВМ отложены владельцем на этапе хакатона; нет гарантии
восстановления при потере диска. Ссылка mini-app остаётся прежней: обновляем ревизию
существующего контейнера, не создаём новый контейнер и не меняем привязку MAX.

Текущий HTTPS-адрес `https://bbapc7qgk242slpm2df5.containers.yandexcloud.net/`
уже привязан к боту MAX. Выкладка создаёт новую ревизию этого контейнера и не
меняет адрес. После автоматических проверок откройте mini-app из чата MAX и
проверьте сценарий на мобильном устройстве. Не отправляйте организаторам токен,
URL репозитория, localhost или временный tunnel вместо ссылки приложения.

После успешной выкладки проверьте подписки read-only командой `node --use-system-ca scripts/max-webhook.mjs`.
Если список пуст, подключите webhook: `node --use-system-ca scripts/max-webhook.mjs --apply --url=https://bbapc7qgk242slpm2df5.containers.yandexcloud.net/api/max/webhook`.
Скрипт не перезаписывает существующую подписку и не выводит токен или секрет. Затем напишите боту реальный запрос, проверьте план в чате и открытие той же версии в mini-app.

Если бот молчит, проверьте `node scripts/diagnose-max-webhook.mjs --since=<UTC-время>`:
скрипт выводит только статусы и безопасные коды ошибок. Вебхук возвращает 503,
если не удалось отправить ответ в MAX, и платформа повторяет доставку. Для
исходящих запросов к MAX сервер использует опубликованный российский корневой
сертификат из `src/server/max-ca.ts` только для этого API; проверка TLS не
отключена. При смене цепочки сертификатов MAX сверяйте её с официальным
источником, не добавляйте в код промежуточные или непроверенные сертификаты.

Если при открытии из MAX планировщик не пускает, различайте два сообщения.
«MAX не передал данные для входа» означает, что клиент не получил подписанные
`WebAppData` ни через MAX Bridge, ни из URL-фрагмента: проверьте, что у бота
подключено именно мини-приложение, а не обычная ссылка на сайт. «Не удалось
подтвердить сеанс MAX» означает, что данные пришли, но сервер их отклонил.
В логах запроса `/api/planning/bootstrap` фиксируется только код причины
(`invalid_hash`, `expired` и т. п.), без токена и данных пользователя. При
`invalid_hash` сверьте токен в Lockbox с ботом, к которому прикреплено приложение;
при `expired` закройте окно и откройте заново. Не пересылайте никому полный
URL с `WebAppData`, значение `initData` или заголовок `X-Max-Init-Data`.

