# Планировщик городского досуга для MAX

Планировщик получает пожелания и ограничения, подбирает реальные места и выбранные события и проверяет, помещаются ли посещения и дорога в доступное время. Основная цепочка: сообщение боту MAX → необязательный разбор Alice Flash → подтверждение условий → 2ГИС Places/Routing и выбранные события KudaGo → Python/OR-Tools → план в чате и мини-приложении. LLM не выбирает окончательный маршрут. Вместо свободного текста можно задать занятия вручную в мини-приложении.

Бот и мини-приложение используют общее состояние PostgreSQL. Учебные места не подставляются при сбоях внешних API. Текущий исходник развивается; окончательная версия сдачи ещё не зафиксирована. Статус опубликованной версии и непроверенные ограничения приведены ниже.

## Запуск приложения

1. Установите Docker Desktop с Compose.
2. Если `.env.local` ещё нет, скопируйте `.env.example` в `.env.local` и заполните MAX, 2ГИС и отдельный `POSTGRES_PASSWORD`. Yandex нужен для разбора текста, отдельный MapGL-ключ — для карты. При установленном Node.js файл можно безопасно создать командой `npm.cmd run env:init`. Для пароля Compose используйте случайную строку из букв/цифр (другие символы требуют URL-кодирования в DATABASE_URL).
3. Из корня продукта запустите:

```powershell
docker compose --env-file .env.local up --build -d
```

Compose запускает приложение и PostgreSQL. Локальный адрес: http://127.0.0.1:3000. Вне MAX вход в планировщик закрыт, учебная авторизация в рабочем сервере отсутствует. Для реального запуска из MAX разместите контейнер по HTTPS, подключите постоянную базу в РФ, задайте ссылку mini-app у бота и настройте webhook после выкладки.

Проверка запуска: `docker compose --env-file .env.local ps` и `GET http://127.0.0.1:3000/api/health` (200). Запрос `/api/planning/bootstrap` без подписи MAX должен вернуть 401, а не открыть чужой маршрут. Это проверка сервера, не внешних данных. Перезапуск: `docker compose --env-file .env.local restart app`. Остановка: `docker compose --env-file .env.local down`; повторный запуск — команда из шага 3. Том базы остаётся; `down -v` удалит данные, не используйте его для обычной остановки.

Для разработки без пересборки Docker: установите Node-зависимости (`npm.cmd ci`), Python по [planner/README.md](planner/README.md), укажите `DATABASE_URL` доступной PostgreSQL и выполните `npm.cmd run dev`. Фронтенд — 5173, API — 3000.

## Пользовательский сценарий

- При первом запуске MAX показывает свою кнопку «Начать»; событие запуска даёт боту возможность отправить приветствие и кнопки. Для уже открытого чата доступны `/start` и меню под сообщениями. Штатную кнопку до первого сообщения нельзя создать средствами нашего сервера.
- «Новый маршрут», «Мои маршруты», «Выйти из планирования» и команды `/new`, `/routes`, `/exit`, `/menu` управляют режимом чата. Под сообщением видны только действия, уместные на текущем этапе: вне планирования нет кнопки выхода, при ожидании нового пожелания нет повторной кнопки создания, при уточнении первыми идут варианты ответа. Старые inline-кнопки остаются в истории MAX, но сервер проверяет активный маршрут при нажатии. В открытом маршруте случайный свободный текст не начинает другой план. В списке можно выбрать ранее созданный маршрут или удалить его с подтверждением.
- Написать боту обычными словами, чем и когда хочется заняться. Если город неясен, бот спросит его один раз; неизвестный город не заменяется Москвой.
- Сервер получает каталог выбранного региона и делает один запрос Alice Flash. «Погулять» без иного транспорта предлагает пеший режим.
- Бот показывает «Я правильно понял?» и только первый необходимый вопрос. Старт задаётся кнопкой геолокации, выбором точки на карте (при доступном MapGL) или вводом адреса с выбором найденного дома; уже распознанные условия не приходится заполнять повторно.
- Подтвердить условия кнопкой и получить план с местами, временем посещения, дорогой и примерными расходами прямо в чате.
- При желании открыть mini-app для подробной ленты, карты и правок выбранного в чате маршрута. Изменения полей и навигация не вызывают LLM.

В мини-приложении реализованы изменение условий, список и удаление собственных маршрутов, проверяемая замена остановки и ссылка для просмотра/копирования условий. Замена сначала показывает проверенный вариант и применяется отдельным действием. Карта использует геометрию фактических переходов провайдера; при её отсутствии прямые линии не подставляются. Для отображения нужен отдельный разрешённый браузерный MapGL-ключ. Фотографии мест пока не подключены.

Афиша KudaGo доступна для поддержанных городов, включая Нижний Новгород и Казань. Выбор карточки, проверка сеанса и добавление события — отдельные шаги. Фиксированный сеанс включается целиком; для выставки с часами площадки пользователь задаёт длительность. Перед расчётом источник и площадка проверяются заново. Неизвестные часы, неподходящий возраст, смена сеанса или площадки не превращаются в подтверждённое посещение. Выбранное событие сохраняется вместе с остальными пожеланиями. Билеты и бронирование не продаются; наличие билетов и запись не подтверждаются.

Общественный транспорт поддержан алгоритмом и адаптером с проверкой конкретного времени отправления, ожиданий и пересадок. Возможность появляется только при подтверждённом доступе провайдера для города; действующий ключ и живой маршрут ОТ ещё требуют проверки. Стоимость проезда неизвестна. Смешанные способы передвижения в одном плане не поддерживаются. Прогулка между несколькими местами требует пешего режима; посещение одного парка может сочетаться с другим транспортом между занятиями. Длительности обычных посещений задаются версионированной политикой, неизвестные цены и расписания не выдумываются.

Ссылка передаёт собственные условия и только ещё свежий результат, без исходного запроса и адресных поисковых строк. До создания показано, что входят даты, занятия, бюджет, требования и состав группы, включая указанный возраст детей. Точные пользовательские точки включаются отдельным выбором. Ссылка доступна любому её обладателю после входа MAX, действует не более 7 суток и отзывается автором. Копия получателя принадлежит ему, требует нового подтверждения и расчёта; она не меняет план автора. Открытие выбора чата в MAX не считается подтверждением доставки.

Бюджет по умолчанию строгий: для него нужна подтверждённая верхняя граница цены. При её отсутствии бот и форма предлагают явный выбор «по среднему чеку на человека» с числом участников и повторным подтверждением условий. В этом режиме сумма — ориентир, её соблюдение не гарантируется. Цена с неизвестным значением остаётся неизвестной; бесплатность парков не предполагается. Поэтому приблизительный бюджет также может дать неполный план. Выбор «без лимита» не превращает неизвестную стоимость в ноль.

Число кандидатов для маршрута подбирается по доступному бюджету матрицы и последующих проверок пути: сначала по одному для каждого занятия, затем расширение по очереди. Фиксированного ограничения в четыре кандидата нет. Если даже минимальный набор не укладывается в ограничения расчёта, возвращается `ROUTING_SCOPE_TOO_LARGE` с просьбой разделить занятия. Если занятие пропущено, планировщик проверяет допустимые альтернативы из уже полученных мест и необходимые переходы к ним в пределах оставшегося бюджета. Полученный маршрут проходит повторную проверку на фактическое время отправления; недоступный переход не заменяется прямой линией.

Places сначала получает первые страницы всех групп пожеланий, затем следующие по очереди. Каждый физический HTTP-запрос, включая переключение ключа, расходует общий бюджет операции; для Routing отдельно учитывается число пар. Частичные данные сохраняются при исчерпании бюджета. Отсутствующий, некорректный или противоречивый `total` не доказывает полноту результатов. Бот и mini-app показывают радиус поиска и неполное покрытие. По умолчанию ищем в 5 км от старта; в «Изменить условия → Старт и финиш» можно явно задать другой радиус до 50 км. Это расстояние от старта, а не длина всего пути. Настройка сохраняется и передаётся с условиями; после изменения нужны подтверждение и пересчёт. Та же граница проверяется планировщиком для мест и выбранных событий. HTTP/page/pair budgets не повышаются: подходящее место за границей или за пределами полученных страниц всё ещё может быть пропущено. Радиус автоматически не расширяется.

## Постоянное состояние и ограничения

PostgreSQL хранит черновики, версии, счётчики обращений и квитанции действий для нескольких экземпляров сервера. TTL черновика — 30 минут, выдачи результата — 5 минут. Список маршрутов хранится отдельно до 30 дней после изменения навигации. Новые маршруты и принятые правки также создают отдельную запись **пользовательских условий** на 30 дней после изменения условий: бюджет и его режим, число участников, транспорт, календарные даты/часы, занятия, порядок, ограничения и происхождение значений. Выбранные пользователем точки сохраняются с происхождением; подписи адресов и координаты из результатов поиска не переносятся в эту запись. Каталог, ID рубрик/мест, карточки, расписания, цены и результат маршрута в ней отсутствуют.

Открытие сохранённых условий после истечения черновика работает в боте и mini-app без LLM/Places/Routing. Для продолжения пользователь явно выбирает город заново; сервер связывает поддержанные типы с новым каталогом и создаёт неподтверждённый черновик. Календарные даты не сдвигаются автоматически, адресные точки нужно выбрать повторно. Старые callback-версии не становятся действительными после восстановления. Изменение краткоживущего черновика и сохранение условий выполняются одной SQL-транзакцией; чтение, подтверждение и повторное открытие не продлевают срок хранения условий.

Восстановление поддерживает прогулку, питание и однозначно сопоставленные именованные типы. Неизвестные типы, сложные исключения и неподдержанные ограничения не удаляются автоматически: условия остаются доступны, новый расчёт требует уточнения. Старые записи без отдельного снимка показывают честное предупреждение: в них остался только исходный запрос и прежние правки восстановить нельзя. Новый разбор по такому запросу — отдельное явное действие. Удаление маршрута удаляет сохранённые условия и доступный черновик. Очистка просроченных записей выполняется при запуске и раз в минуту. Это сохранение условий поездки, **не долговременное сохранение прежних карточек и геометрии маршрута**; вопросы использования/retention краткоживущих provider-фактов остаются отдельными.

Миграция `src/server/planning-schema.sql` добавляет только таблицы/индексы, выполняется при старте под advisory lock. Нужна прямая PostgreSQL-сессия или session pooling; transaction-mode PgBouncer не поддерживается. Для отката приложения таблицы не удалять. `DATABASE_CA_PATH` включает проверяемый TLS с CA — не отключайте проверку сертификата.

Повтор event_id не повторяет оплаченный запрос; после обрыва с неизвестным исходом требуется новое явное действие. Суточных и поминутных квот на количество запросов, расчётов и поисков нет; таблица суточного использования остаётся только для учёта. Сохраняются ограничения размера входных данных, таймауты, предотвращение одновременных дублей и два одновременных разбора/расчёта на базу. При создании нового маршрута каталог категорий запрашивается один раз: используется вложенное дерево полной корневой страницы, без дополнительных запросов по каждой родительской категории и без кэша между запросами. Если дерево неполно или недоступно, маршрут не создаётся. Это не независимая сверка всех дочерних списков; она остаётся отдельной процедурой offline-оценки. При явном ответе 2ГИС об исчерпании лимита конкретного сервиса сервер один раз переключается на резервный ключ; остальные сервисы остаются на основном. Резерв не помогает, если оба ключа относятся к подписке с общим исчерпанным лимитом. Неизвестные ошибки, таймауты и неверные параметры не вызывают смену ключа. Без внутренних квот платные обращения могут увеличить расходы: контролируйте счёт и бюджет в Yandex Cloud и 2ГИС.

Planning API, включая ручной ввод, афишу, библиотеку, замены и ссылки, описан в `openapi.yaml`. Все его методы требуют `X-Max-Init-Data: <подписанный initData>`. Yandex Serverless Containers удаляет входящий `Authorization`, поэтому его нельзя использовать для передачи данных запуска. Без необходимых MAX/2ГИС/БД параметров bootstrap возвращает 503, без валидной подписи — 401. Отсутствие ключей Yandex отключает только разбор текста: ручной ввод и работа с сохранёнными условиями остаются доступны. Фиктивной авторизации в production нет.

### Адаптер Alice Flash

`src/server/intent-start.ts` переносит первоначальное извлечение в продукт; runtime не зависит от соседнего служебного каталога. Prompt v0.8, JSON-schema v0.2, postprocessing и серверные предложения времени лежат в `src/server/intent/`; ресурсы копируются в серверную сборку. Неопределённые единицы бюджета остаются `unknown`, блокируют подтверждение и выбираются в форме.
Дополнительная версионированная проверка сверяет поддержанные явные пожелания с извлечёнными занятиями, рубриками, днями и порядком. Поддержанные семейства — питание, прогулка, культура, кино, спорт; это ограниченная проверка, а не гарантия понимания произвольного текста. Для разрешённых ошибок структуры/категорий/семантики допускается не более одного дополнительного платного вызова Alice; оба вызова отражаются в счётчике использования. Повторно невалидный ответ не превращается в план автоматически.

`YandexIntentClient` — серверный транспорт Alice Flash: фиксированный официальный endpoint, structured output, 30 секунд, максимум 4096 выходных токенов, `store:false` и `x-data-logging-enabled:false`, без retries и смены модели. При создании обязательно задаются ключ, folderId, `maxCalls`, `maxEstimatedRub`; ключ не входит в браузерный ответ. Оценочный резерв на каждую попытку — 7,3728 ₽ по проверенному 24.09.2026 тарифу, без возврата резерва после ошибок. Это локальный ограничитель по зафиксированному тарифу, **не гарантия списания**; отдельный облачный бюджет и актуальность тарифа нужны при реальном запуске.

Последняя подтверждённая публикация — ревизия `bbasijvvpno79vivq7f8` от 27.09.2026; новые функции текущего рабочего дерева ещё не опубликованы. В авторизованном MAX web через Edge 27.09 проверены: прогулочный план на 18–20 с тремя точками и предупреждением о неизвестных часах; сохранение прогулки и еды как двух пожеланий; отказ выдать выполненный план для 20 минут. При этом двухчасовой сценарий «погулять, потом поесть» завершился ошибкой проверки переходов. Мини-приложение удалось открыть в 17:36 МСК, но сохранение правки получило 404 «черновик недоступен», а восстановление затем завершилось сетевой ошибкой. Причина недоступности черновика этим ответом не установлена. Повторная публикация вечером остановилась до создания ревизии: Cloud API и Container Registry стали недоступны с рабочего компьютера. Полная готовность MAX web/mobile не подтверждена.

Unit/integration tests используют синтетические ответы провайдеров, реальные PostgreSQL и Python для соответствующих интеграционных сценариев. Локально проверены выбранное событие + еда через HTTP/SQL/Python, повтор без нового расчёта и сохранность после пересоздания координатора. Это не доказательство доступности живой афиши. Полный региональный каталог передаётся парсеру сервером; несколько типов в offline fixture — учебные данные, не фильтр рабочего продукта. Прогулка с неподтверждёнными часами выдаётся только как предварительный план с предупреждением.

## Контракт собственного API и проверка поставки

[openapi.yaml](openapi.yaml) описывает HTTP-методы, авторизацию и схемы ответов. [DATA-API.yaml](DATA-API.yaml) содержит обязательные проверки, а [test-data/api-scenarios.json](test-data/api-scenarios.json) — синтетические сценарии. Документы используют JSON-нотацию YAML 1.2. Поля окончательной ревизии остаются незаполненными до фиксации поставки; тестовый доступ MAX передаётся проверяющим приватно.

Проверка актуальности: `node --import tsx scripts/api-contract.mts`. После изменения Zod-контрактов: та же команда с `--write`, затем тесты. Общая локальная проверка: `npm run check` и `npm run planner:test`. Для PostgreSQL-проверок задайте `TEST_DATABASE_URL` **отдельной временной базы** перед `npm test`; рабочую базу для тестов не используйте. Без этой переменной проверки БД пропускаются. Прохождение локальных тестов не подтверждает качество реальных данных, маршрутов и отображения в MAX.

## API и граница доверия

- `GET /api/health` — process health endpoint, не проверка доступности внешних API;
- `GET /api/public-config` — только публичная конфигурация MapGL, без серверных ключей Places/ Routing;
- `POST /api/auth/max` — принимает только `{ "initData": "..." }`, проверяет подпись, `auth_date` и пользователя;
- `POST /api/max/webhook` — проверяет `X-Max-Bot-Api-Secret`, обрабатывает личные сообщения и callbacks бота;
- остальные GET-запросы с `Accept: text/html` возвращают SPA.

Frontend не доверяет `initDataUnsafe` и не получает `MAX_BOT_TOKEN`. В обычном браузере он просит открыть приложение из MAX; сервер проверяет подпись при каждом planning-запросе. Логи редактируют `X-Max-Init-Data`, `Authorization` и `initData`.

Диагностический экран MapGL открывается локально по `http://127.0.0.1:5173/?map=2gis-smoke`. Он не заменяет основной экран продукта. Один demo key можно временно повторить в трёх локальных переменных, но production в таком случае не отдаст MapGL-ключ браузеру: для развёртывания нужен отдельный ключ с ограничением по origin. 2ГИС разрешает создать бесплатный demo key только один раз; дополнительные ключи доступны в рамках подписки, поэтому наличие отдельного production-ключа нужно проверить в Platform Manager заранее. Сырые ответы Places/Routing используются только внутри расчёта; нормализованный пользовательский результат кратковременно сохраняется в PostgreSQL. Права на это хранение до публичного запуска проверяются отдельно.

## Ядро пользовательского запроса

- `src/shared/planner-domain.ts` содержит строгие Zod-контракты request-слоя версии `planner-domain.v0.1`;
- `src/server/intent-parser.ts` преобразует текст в `PlanningRequestDraft`, но не угадывает отсутствующие город, границы времени, точку старта или транспорт;
- parser-core использует только детерминированные правила. Его словарь интересов — стартовая ограниченная таксономия, а не универсальная NLP-модель;
- `selectNextClarificationQuestion` сохраняет порядок `BLOCKER → SAFETY → QUALITY`;
- `confirmPlanningRequestDraft` создаёт `PlanningRequest` только из состояния `READY_FOR_CONFIRMATION`.

Этот прежний детерминированный parser-core сохранён для тестов; рабочий первоначальный ввод использует Alice Flash и последующую строгую валидацию. Чатовый адаптер хранит шаг уточнения и квитанции событий в общем состоянии владельца; повтор доставленного события не должен повторять оплаченный разбор. Живой проход через MAX обязателен перед заявлением о готовности.

## Production и привязка к MAX

### Существующий Yandex Serverless Container и PostgreSQL на ВМ

Для облачного TLS передайте `DATABASE_URL` и публичный CA через `DATABASE_CA_PEM`
из Lockbox; альтернативно укажите `DATABASE_CA_PATH` внутри контейнера. Не задавайте
оба CA-параметра одновременно и не добавляйте SSL-параметры в строку подключения.
Production требует CA. Локальный Compose явно допускает plaintext только к своему
сервису `database`; исключение не переносить в облако.

`node scripts/configure-yandex-secrets.mjs` проверяет наличие необходимых локальных
настроек без сети. С `--apply` читает DATABASE_URL и публичный CA по SSH с уже
доверенного сервера, обновляет существующий Lockbox новой версией на основе прежней
(остальные поля сохраняются) и выдаёт существующему runtime SA payloadViewer только
на этот секрет. Подготовленные ключи берутся из `.env.local`; значения не печатаются
и не записываются во временные файлы. Закрытые TLS/SSH-ключи не передаются в Lockbox.
После успешного add-version сохраните показанный Version ID. При сбое после этой
операции проверьте версии перед повтором — создание новой версии не идемпотентно.
Подготовка **не** переключает ревизию приложения и не делает LLM-запросов. Новую
версию секрета при rollout следует закреплять явно, сохраняя все secret mappings.

После выкладки навигации можно выполнить `npm.cmd run max:commands -- --apply`:
скрипт сохранит существующие команды бота и добавит `/start`, `/new`, `/routes`,
`/exit`, `/menu`. Сначала запустите `npm.cmd run max:commands` без `--apply` и
проверьте список. Inline-кнопки в сообщениях работают и без регистрации команд.

После успешной подготовки Lockbox запустите из корня проекта
`npm.cmd run deploy:yandex:live` в PowerShell с работающими `yc` и Docker.
Скрипт проверит существующую ревизию и URL, соберёт и отправит образ в Container
Registry, выпустит новую ревизию **того же** Serverless Container с закреплённой
версией секрета, приватной VPC-сетью и проверяемым TLS к PostgreSQL, затем проверит
`/api/health`, закрытый `/api/planning/bootstrap` и публичную конфигурацию.
`PORT` не передаётся как переменная ревизии: Yandex Cloud запрещает её задавать;
в Docker-образе приложение уже слушает порт 8080.
При неудачной HTTP-проверке он попытается вернуть прежнюю ревизию. Скрипт не делает
платных запросов к LLM или 2ГИС. Проверка API не заменяет ручной проход по экрану
внутри MAX. Если версия Lockbox после подготовки изменилась, сначала проверьте её:
скрипт намеренно остановится, не выбирая секреты по умолчанию.
Если образ уже загружен, но команда создания ревизии завершилась ошибкой, запустите
`node scripts/deploy-yandex-live.mjs --apply --reuse-image-tag=<ранее загруженный тег>`:
это пропустит повторную сборку и загрузку. При отказе CLI выводится одна
укороченная строка причины с маскированием URL БД, токенов и ключей.

Если браузер работает через системный прокси, терминал может не использовать его.
Для Node 24.15 примените `HTTP_PROXY`/`HTTPS_PROXY` только в своей оболочке и запустите
`node --use-system-ca --use-env-proxy scripts/deploy-yandex-live.mjs --apply`.
Недоступный локальный proxy endpoint или тайм-аут TCP к Cloud API/реестру нельзя
исправить сменой npm-команды. Не отключайте проверку TLS.
Docker сразу проверяет загрузку Vite и платформенного TypeScript после `npm ci`:
недокачанный optional native-пакет не должен сохраниться как успешный слой зависимостей.

Резервные копии вне ВМ отложены владельцем на этапе хакатона; нет гарантии
восстановления при потере диска. Ссылка mini-app остаётся прежней: обновляем ревизию
существующего контейнера, не создаём новый контейнер и не меняем привязку MAX.

Текущий HTTPS-адрес `https://bbapc7qgk242slpm2df5.containers.yandexcloud.net/`
уже привязан к боту MAX. Выкладка создаёт новую ревизию этого контейнера и не
меняет адрес. После автоматических проверок откройте mini-app из чата MAX и
проверьте сценарий на мобильном устройстве. Не отправляйте организаторам токен,
URL репозитория, localhost или временный tunnel вместо ссылки приложения.

После успешной выкладки проверьте подписки read-only командой `node --use-system-ca scripts/max-webhook.mjs`.
Если список пуст, подключите webhook: `node --use-system-ca scripts/max-webhook.mjs --apply --url=https://bbapc7qgk242slpm2df5.containers.yandexcloud.net/api/max/webhook`.
Скрипт не перезаписывает существующую подписку и не выводит токен или секрет. Затем напишите боту реальный запрос, проверьте план в чате и открытие той же версии в mini-app.

Если бот молчит, проверьте `node scripts/diagnose-max-webhook.mjs --since=<UTC-время>`:
скрипт выводит только статусы и безопасные коды ошибок. Вебхук возвращает 503,
если не удалось отправить ответ в MAX, и платформа повторяет доставку. Для
исходящих запросов к MAX сервер использует опубликованный российский корневой
сертификат из `src/server/max-ca.ts` только для этого API; проверка TLS не
отключена. При смене цепочки сертификатов MAX сверяйте её с официальным
источником, не добавляйте в код промежуточные или непроверенные сертификаты.

Если при открытии из MAX планировщик не пускает, различайте два сообщения.
«MAX не передал данные для входа» означает, что клиент не получил подписанные
`WebAppData` ни через MAX Bridge, ни из URL-фрагмента: проверьте, что у бота
подключено именно мини-приложение, а не обычная ссылка на сайт. «Не удалось
подтвердить сеанс MAX» означает, что данные пришли, но сервер их отклонил.
В логах запроса `/api/planning/bootstrap` фиксируется только код причины
(`invalid_hash`, `expired` и т. п.), без токена и данных пользователя. При
`invalid_hash` сверьте токен в Lockbox с ботом, к которому прикреплено приложение;
при `expired` закройте окно и откройте заново. Не пересылайте никому полный
URL с `WebAppData`, значение `initData` или заголовок `X-Max-Init-Data`.

## Структура

Маршрутизация в production использует последовательные измеренные вставки:
сначала покрывает занятия, затем улучшает прогулку. На операцию выделено до
10 объектов Routing, включая повторную проверку выбранных переходов. Это
ограниченный поиск, а не оптимум среди всех мест города. При отказе дороги
показываются найденные кандидаты без выдуманного расписания.

Общий SQL-счётчик Routing переживает перезапуск и применяется ко всем серверным
ключам вместе: по умолчанию 5 объектов за скользящую минуту, 50 за день, 1000
за период с 20-го числа. День начинается в 00:00 Москвы. Перед первой выкладкой
задайте `DGIS_ROUTING_INITIAL_DAY`, `DGIS_ROUTING_INITIAL_DAY_USED`,
`DGIS_ROUTING_INITIAL_MONTH`, `DGIS_ROUTING_INITIAL_MONTH_USED` по данным владельца
подписки. Пустая инициализация закрывает доступ; новый деплой не перезаписывает
существующие счётчики. Расход за пределами этого приложения автоматически не
известен: числа приложения не являются текущим балансом провайдера. Для другой
подписки сверьте лимиты и календарь до запуска. Отправленные попытки, включая
отказ ключа и таймаут, учитываются без возврата расхода. Квотная SQL-транзакция
завершается до ожидания и HTTP. В базе нет ключей и координат маршрутов.

Живые диагностические `verify-manual-route.mts` и `verify-live-journey.mts`
тоже требуют ту же БД и проверяемый TLS, записывают только счётчики квоты.
Низкоуровневые `smoke:2gis`/`probe-*` обращаются напрямую и предназначены для
ручной диагностики по отдельно проверенной квоте; не запускайте их сериями.
Откат к версии до общего счётчика снова допускает старый расход: такой откат
требует остановки новых расчётов или ограничения Routing у провайдера.

Время обычного посещения является оценкой и меняется в условиях маршрута.
Сеанс выбранного события сохраняет расписание источника. Неизвестные возрастные
ограничения обычного места показываются предупреждением; известное ограничение
и возрастной допуск выбранного события проверяются обязательно. Неподдерживаемое
пожелание снимается только явным действием пользователя; оно не считается выполненным.

```text
src/client/  React/MAX UI и MAX Bridge
src/server/  Fastify API, разбор окружения, проверка initData
src/shared/  общие типизированные контракты
scripts/     воспроизводимые локальные команды
```
