# V-MAX

Планировщик городского досуга в MAX. Пользователь задаёт пожелания, город, время, старт и бюджет; бот и мини-приложение подбирают места и выбранные события, сохраняют план и показывают остановки на карте.

- [Открыть бота](https://max.ru/t801_hakaton_max_bot)
- [Мини-приложение и API](https://bbapc7qgk242slpm2df5.containers.yandexcloud.net/) — вход через MAX.
- [Исходный код](https://github.com/kartenplanexe/V-MAX), рабочая ветка `main`.

По умолчанию включён режим `external`: V-MAX оценивает время посещений и переходов, а дорогу строит 2ГИС. Кнопка «Посмотреть на карте» открывает в 2ГИС старт, все остановки по порядку и финиш. Купить билеты или забронировать столик нужно у организатора или заведения.

## Быстрый запуск

Нужен Docker с Compose. Создайте `.env.local` из [.env.example](.env.example) и заполните необходимые значения из таблицы ниже. `POSTGRES_PASSWORD` задайте отдельным паролем из букв и цифр. Рабочие ключи не включаются в Git и передаются проверяющим по закрытому каналу.

Все локальные компоненты запускаются одной командой:

```sh
docker compose --env-file .env.local up --build -d
```

Compose поднимает приложение и PostgreSQL 17. Приложение доступно на `http://127.0.0.1:3000`, база — только во внутренней сети Compose на порту 5432. Миграции выполняются приложением при запуске. Python и Node-зависимости устанавливаются внутри образа из lockfiles.

Проверка запуска:

```sh
curl http://127.0.0.1:3000/api/health
```

Ожидается HTTP 200. Запрос к `/api/planning/bootstrap` без подписанных данных MAX должен возвращать 401. Чтобы пройти весь сценарий, разместите приложение по публичному HTTPS-адресу и подключите его к боту. Авторизация происходит при открытии приложения из MAX. MAX, 2ГИС, KudaGo и Alice Flash работают через внешние API.

Остановка и повторный запуск:

```sh
docker compose --env-file .env.local down
docker compose --env-file .env.local up --build -d
```

Планы сохраняются в томе `planning-data`. `down -v` удаляет этот том и данные.

## Конфигурация

Полный перечень переменных и значения по умолчанию — в [.env.example](.env.example).

| Переменная | Назначение |
|---|---|
| `MAX_BOT_TOKEN`, `MAX_BOT_USERNAME` | Токен и username выданного бота; авторизация mini-app и Bot API. |
| `PUBLIC_BASE_URL` | Публичный HTTPS-адрес приложения при работе внутри MAX. |
| `POSTGRES_PASSWORD` | Пароль локальной PostgreSQL. Compose формирует `DATABASE_URL` сам. |
| `DATABASE_URL` | Подключение к PostgreSQL вне Compose. |
| `DATABASE_CA_PATH` или `DATABASE_CA_PEM` | CA для проверяемого TLS-подключения к облачной БД; используется один вариант. |
| `DGIS_PLACES_API_KEY` | Серверный поиск мест и адресов в 2ГИС. |
| `DGIS_MAPGL_API_KEY` | Ключ встроенной карты; передаётся браузеру, должен иметь ограничения разрешённых origin. |
| `DGIS_MAPGL_ALLOW_SHARED_DEMO_KEY` | Разрешение использовать общий демо-ключ для карты. По умолчанию выключено; такой ключ публичен. |
| `DGIS_BACKUP_API_KEY`, `DGIS_TERTIARY_API_KEY` | Необязательные резервные ключи 2ГИС. |
| `YANDEX_API_KEY`, `YANDEX_FOLDER_ID` | Доступ к Alice Flash для разбора свободного текста. Без них остаётся ручной ввод. |
| `PLANNING_ROUTING_MODE` | `external` по умолчанию. `verified` включает внутреннюю проверку дорог и требует Routing API. |
| `DGIS_ROUTING_API_KEY`, `DGIS_ROUTING_*` | Ключ, общие квоты и начальные счётчики использования для режима `verified`. |
| `MAX_WEBHOOK_ASYNC` | Фоновая обработка на поддерживаемой облачной платформе. В локальном Compose оставить пустым. |

Для KudaGo ключ не требуется. В облаке серверные секреты поступают из Lockbox. Для проверки публичного бота используется собственный аккаунт MAX; отдельной административной роли в пользовательском сценарии нет.

## Сценарий проверки в MAX

1. Откройте бота и выберите «Новый маршрут». Введите, например: «Завтра с 14 до 18 хочу погулять пешком в Нижнем Новгороде, а потом поесть».
2. Укажите старт: выберите точку на карте, передайте местоположение или введите адрес. Проверьте распознанные условия.
3. Запустите подбор. Ожидается план с местами для прогулки и еды либо понятное сообщение, если условия несовместимы или источник недоступен.
4. Откройте мини-приложение. Переключите «План» / «Карта», выберите маркер и откройте общий маршрут в 2ГИС.
5. В «Добавить событие» выберите категорию и событие на нужный день. Укажите сеанс или длительность посещения, подтвердите и пересчитайте. Выбранное событие должно присутствовать в плане со временем и ссылкой на источник; неподходящий сеанс не должен молча заменяться другим местом.
6. Измените время, бюджет или радиус. Стрелки бюджета меняют значение на 100 ₽, радиуса — на 1 км. Окончание раньше начала должно вызвать ошибку с возможностью исправить ввод.
7. Откройте «Мои маршруты», вернитесь к подборке или поделитесь её условиями. Через 30 минут появляется предложение обновить данные; готовая подборка остаётся доступной до удаления.

Время «вечером» по умолчанию — 17:00–20:00, «днём» — 13:00–16:00, «утром» — 09:00–12:00. Явно заданные часы имеют приоритет. При пустом результате измените запрос или условия и повторите подбор. Ошибка внешнего сервиса не подменяется учебными местами.

## Разработка и автоматические проверки

Для запуска вне Docker: Node.js 24.15.0, Python 3.12 и `uv` 0.11.14. Версии зависимостей закреплены в `package-lock.json` и `planner/uv.lock`.

```sh
npm ci
uv sync --project planner --frozen --python 3.12.13
npm run check
npm run planner:test
npm run check:secrets
```

`npm run check` выполняет типизацию, TypeScript-тесты и сборку. SQL-тестам нужна **отдельная тестовая PostgreSQL** в переменной `TEST_DATABASE_URL`; без неё они пропускаются. CI предоставляет такую базу. Длительная проверка фонового расчёта включается отдельно через `RUN_LONG_ASYNC_ACCEPTANCE=1`. Не используйте рабочую БД для тестов. Скан секретов использует Docker с закреплённым образом Gitleaks.

Для разработки настройте `.env.local`, PostgreSQL и выполните `npm run dev`: Vite использует порт 5173, API — 3000. Вход в приложение — через MAX.

Для локального примера без ключей и аккаунта MAX:

```sh
npm run planner:form:demo
```

Откройте `http://127.0.0.1:4174/planner-form`. Пример работает с вымышленными местами и временем дороги; расчёт выполняет Python-планировщик. Здесь можно менять условия, получать план и проверять ошибки формы. Афиша, сохранение в облаке и функции MAX проверяются в рабочем боте. Консольный пример: `npm run planner:demo`. Для обоих примеров нужно установленное выше Python-окружение.

## Архитектура и данные

- `src/client/` — React, MAX UI, MAX Bridge и карта MapGL.
- `src/server/` — Fastify API, webhook бота, проверка доступа, адаптеры источников и PostgreSQL.
- `src/shared/` — общие контракты и модели.
- `planner/` — детерминированный планировщик Python / OR-Tools.
- `scripts/` — сборка, проверка контрактов и лицензий, настройка и развёртывание.

LLM извлекает условия из текста, но не подтверждает цены, расписания или время дороги. 2ГИС Places даёт места и адреса; MapGL отображает карту. KudaGo предоставляет события, сеансы, площадки и сведения о билетах. Программа сопоставляет их с условиями пользователя. При известной ограниченной цене входа бюджет учитывает верхнюю границу для группы; неизвестная цена не становится нулевой.

PostgreSQL хранит идентификатор пользователя MAX, условия, состояние диалога и сохранённые подборки. У мест и событий сохраняются источник и время получения. Готовые подборки доступны до удаления пользователем; незавершённые условия — до 30 дней. При обмене планом передаются его условия, а в ссылке 2ГИС — координаты остановок. Не включайте личные сведения в свободный текст.

Пояснение об обработке данных доступно в mini-app по `/?page=information` и через `/privacy` в боте. Реквизиты оператора пока не заполнены; пояснение не является утверждённой политикой. Лицензии и сведения о сторонних компонентах — в [THIRD_PARTY_NOTICES.md](THIRD_PARTY_NOTICES.md).

## Развёртывание

Скрипт для существующего контейнера Yandex Cloud:

```sh
node scripts/deploy-yandex-live.mjs --apply --external-places-demo
```

Нужны Docker, `yc`, доступ к настроенным облачным ресурсам и Lockbox. Скрипт проверяет конфигурацию и БД, собирает образ, обновляет ревизию и проверяет health и отказ входа без подписи. После выкладки нужно пройти сценарий внутри MAX. Для подготовки отдельной БД вне Compose есть [инструкция PostgreSQL](deploy/postgres/README.md).

## Ограничения

- Поиск ограничен радиусом и ответами источников. Он не гарантирует сравнение всех мест города. Радиус по умолчанию: пешком 5 км, велосипед 10 км, общественный транспорт/такси 30 км, автомобиль 50 км.
- В `external` время переходов и посещений приблизительное. Дорогу, часы работы, цены и наличие билетов нужно проверить перед выходом. Режим `verified` требует отдельной конфигурации и квоты Routing.
- Покрытие афиши зависит от каталога KudaGo; полное расписание всех кинотеатров не обещается. При изменении даты или устаревании выбора событие перепроверяется.
- Общий маршрут проверен в веб-версии 2ГИС. Полную проверку приложения и переходов на Android и iOS ещё предстоит провести.
- Работа длительных фоновых задач в облаке пока не проверена; такие задачи проверялись только локально.

## Польза, пилот и развитие

V-MAX рассчитан на человека, который хочет провести в городе 2–4 свободных часа: например, погулять, поесть и зайти на выставку. У этих занятий общие ограничения по времени и бюджету, поэтому мы подбираем их вместе. Насколько это быстрее ручного поиска, ещё нужно измерить.

Планируем начать с 15–20 добровольцев в Нижнем Новгороде. Каждый выполнит похожие задания в привычных сервисах и V-MAX; порядок будем чередовать. Измерим время выбора, долю готовых планов, число замен и повторное использование через неделю. Цель — сократить медианное время выбора на 30% без роста числа замен. За наблюдения отвечает продакт-менеджер, за ошибки и расход API — разработчик. На набор и повторную проверку отводим две недели. Пилот ещё не проводился.

Следующий город — Казань: проверим 20 сценариев для центра и окраин, разных способов передвижения, событий и бюджета, включая пустой поиск. Затем — Екатеринбург, где отдельно проверим часовой пояс и даты сеансов. Интерфейс и алгоритм останутся общими; для каждого города нужно сверить рубрики, адреса и доступность афиши.

До запуска в новом городе нужны доступные квоты API, поддержка, мониторинг и резервные копии БД. Чтобы оценить расходы, разделим затраты на API, облако и БД на число готовых планов; отдельно измерим число запросов и задержки. Для рабочего бюджета возьмём коммерческие тарифы поставщиков. Новый город запускаем после проверки сценариев, мобильных клиентов и стоимости обслуживания.
