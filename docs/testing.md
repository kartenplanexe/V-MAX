# Проверка V-MAX

Основной сценарий с ожидаемыми результатами приведён в [README](../README.md#проверка-основного-сценария). Здесь — дополнительные проверки и работа с API.

## Доступ

Для пользовательского сценария откройте [бота](https://max.ru/t801_hakaton_max_bot) своим аккаунтом MAX. Для обмена планом и проверки изоляции нужны два разных аккаунта. Отдельных логинов V-MAX нет.

В HTTP-клиенте передавайте `X-Max-Init-Data`: подписанные данные свежего запуска мини-приложения из MAX. Их можно взять в инструментах разработчика из заголовка собственного запроса `/api/planning/bootstrap`. Срок действия по умолчанию — час; после истечения откройте приложение заново. Не публикуйте этот заголовок: он предоставляет доступ от имени пользователя.

Для запуска своей копии нужны ключи из README. Доступы для жюри и рабочие значения окружения передаются в закрытой технической части сдачи. Публичный репозиторий их не содержит.

## API

- [openapi.yaml](../openapi.yaml) — OpenAPI 3.1: методы, схемы, авторизация и ошибки.
- [DATA-API.yaml](../DATA-API.yaml) — проверки в порядке исполнения, роли, параметры и ожидаемые ответы.
- [api-scenarios.json](../test-data/api-scenarios.json) — синтетические запросы и ожидаемое поведение.

Файлы YAML записаны в совместимой JSON-форме. `DATA-API.yaml` использует версию схемы проекта `v-max.data-api.v1`; исполняемый формат платформы оценки организаторами в предоставленных документах не опубликован.

1. Импортируйте OpenAPI в HTTP-клиент. Используйте опубликованный `base_url` или адрес собственной установки.
2. Выполните проверки `health` и `deny-unsigned-bootstrap`: ожидаются 200 и 401 соответственно.
3. Установите `MAX_TEST_INIT_DATA` из собственного запуска MAX.
4. Выполняйте `checks` последовательно. Раздел `variables` указывает, из какого ответа брать каждый ID и token. Значения извлекаются по JSON Pointer, например `/view/id`.
5. После изменения используйте последнюю `version`, для нового действия — новый UUID в `event_id`. Числа передавайте числами, а не строками.
6. В цепочке `events-*` выберите доступное событие и сеанс. При `duration_required=true` задайте длительность 5–720 минут внутри окна; иначе удалите поле `visit_duration_minutes` из тела запроса. Пустой список или неподходящее расписание останавливает эту цепочку: отметьте её как непроверенную и продолжайте остальные проверки.
7. Проверьте содержимое результата: HTTP 200 само по себе не означает, что маршрут найден или включает все пожелания.

Сценарии не выполняются автоматически самим YAML-файлом. Для локальной проверки контракта после [подготовки окружения](development.md):

```sh
node --import tsx scripts/api-contract.mts --check
npm exec -- vitest run src/server/submission-api-contract.test.ts
```

Эти команды не обращаются к рабочим API. Реальные `requests`, `plan` и поиск расходуют квоту поставщиков. Webhook предназначен для MAX; тестовые входящие события в рабочий webhook отправлять не нужно.

## Тестовые данные

`test-data/api-scenarios.json` содержит придуманные запросы, а не записи пользователей или ответы поставщиков. Выберите случай из `cases`, введите его `request_text` в бота либо используйте `explicit_api_request` в API. Относительные даты относятся ко дню проверки. Если дата задаётся вручную, выберите будущую дату в часовом поясе города.

Этот JSON не нужно импортировать в PostgreSQL. Воспроизводимые автоматические тесты используют отдельные фикстуры и подменяют внешние ответы. Локальный пример без ключей запускается по [инструкции](development.md#пример-без-ключей). В рабочем приложении поиск, события и карта используют реальные API.

## Дополнительные сценарии

| Случай | Что проверить |
|---|---|
| Мало времени: музей, прогулка и еда за 30 минут | Посещения не выходят за окно; невместившиеся занятия обозначены. |
| «Вечером», без точных часов | Предложено 17:00–20:00; время можно изменить. |
| Пешком / велосипед / транспорт / авто | Радиус по умолчанию — 5 / 10 / 30 / 50 км; явный радиус сохраняется. |
| Бюджет на двоих | Учтены число людей и основание бюджета; неизвестная цена не становится нулевой. |
| Событие с фиксированным сеансом | Сеанс сохранён; несовместимость с другими занятиями показана. |
| Устаревшее событие или новая дата | Требуется повторная проверка; событие не заменяется обычным местом. |
| Замена остановки (только `verified`) | Предпросмотр не меняет план; применение выбранной замены меняет его. |
| Повтор одного `event_id` | Операция не выполняется второй раз; другой запрос с тем же ID отклоняется. |
| Чужой ID плана / нет подписи | 404 / 401, без содержимого чужого плана. |
| Удаление собственного плана | Он исчезает из списка; другие планы остаются. |
| Открытие старой кнопки бота | Пользователь получает актуальное состояние или предложение начать заново. |
| Отключён разбор текста | На отдельной установке без Yandex-ключей доступна ручная форма; география всё ещё требует 2ГИС. |
| Сбой источника | Понятное сообщение и возможность повторить; без вымышленных результатов. |

Проверки отказов и отключения ключей проводите на отдельной установке. Для мобильной проверки пройдите основной сценарий в Android и iOS, включая клавиатуру, прокрутку, возврат из 2ГИС и повторное открытие mini-app. Эмуляция размера окна браузера не проверяет поведение клиента MAX.
