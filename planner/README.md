# Подбор мест по подтверждённому JSON

Работающее локальное ядро: Python 3.12 + Google OR-Tools CP-SAT `9.15.6755`. Это оптимизационная модель, не обученная нейросеть. Она выбирает совместимый набор мест, а не просто сортирует отдельные карточки.

Внутренняя связка поиска 2ГИС, матрицы маршрутов, Python и повторной проверки написана и проверена offline. Публичная форма MAX и облачный вызов Python пока **не подключены**; новый dated/batch Routing-контракт ещё не проверялся нашим ключом вживую. Существующий MAX-сайт и его Docker-образ этим модулем не изменяются. Здесь можно воспроизвести расчёт без ключей, интернета и платежей после установки зависимостей.

## Быстрый запуск

Из корня **продуктового** `V-MAX`, не `V-MAX(service)`:

```powershell
cd planner
uv sync --frozen
cd ..
npm.cmd run planner:demo
npm.cmd run planner:flow:demo
npm.cmd run planner:test
```

Нужен установленный `uv`; он создаёт локальное окружение `.venv`, не попадающее в Git. Зависимости и хеши зафиксированы в `uv.lock`. На macOS/Linux вместо `npm.cmd` используйте `npm`. Без Node: `uv run --frozen python run.py --demo` и `uv run --frozen pytest` из `planner`.

В примере все места, цены и времена маршрутов вымышлены и помечены `data_mode=test`. Реальный solver выбирает музей рядом → кафе, 16:15–17:15 → 17:30–18:15; цена 1000 ₽, 20 минут переходов, по 5 минут перед посещениями. Возврат в старт не требуется. Числа длительности/буферов в этом примере — учебная политика, не измеренные нормативы для всех мест.

Отдельное `planner:flow:demo` использует синтетические HTTP-ответы формы Places/Routing, настоящий нормализатор, Python-процесс и solver. Итог: музей 16:17–17:17 → кафе 17:34–18:19, 24 минуты зарезервированных переходов, неизвестные цены показаны как `null`, не ноль. Это проверка всей внутренней связки, но не live-проверка 2ГИС/MAX.

## Собственный JSON

```powershell
npm.cmd run planner:run -- --input job.json
```

Без `--input` Python читает JSON из stdin. Полный образец входа: `npm.cmd run planner:run -- --demo-input`. Прямой `python planner/run.py` использует компактный JSON-протокол stdout, без npm-заголовков. Ошибка входа возвращает `ERROR / INVALID_PLANNING_INPUT`, без отражения исходного текста или секретов.

Корневой контракт `place-selection.v1`:

| Поле | Смысл |
|---|---|
| `as_of` | Доверенное серверное время проверки с часовым поясом; в демо фиксировано для воспроизводимости |
| `intent` | Результат подтверждения текущего draft: `confirmed-daily-intent.research.v1`, город/регион/timezone, дни, занятия, порядок, общие условия, выбранные точки |
| `catalog` | Версия, регион и `leaf_ids` того же каталога, по которому проверены категории |
| `visit_policy` | Версия правил, `by_category` в минутах и `arrival_buffer_minutes`; не факты от LLM |
| `places` | Канонические места: ID, название, регион, координаты, рубрики, интервалы работы по датам, цены, проверенные свойства и source |
| `route_legs` | Направленные переходы: ID и координаты концов, день/дата, режим, покрываемое окно, безопасные минуты, стоимость и source |
| `budget_policy` | `upper_bound` по умолчанию; явное `estimate` допускает расчёт по известным оценкам с предупреждением, не обещая гарантии |
| `retrieval` | Необязательный итог поиска; `coverage=PARTIAL` сохраняется предупреждением результата |

Вместо `places` можно передать `provider_batches`: массив `{region_id, fetched_at, valid_until, data_mode, items}`. `items` — внутренние результаты Places API. Python проецирует только нужные поля, не пишет payload на диск. Реальные данные нельзя коммитить в примеры.

`intent` — **не сырой JSON LLM и не клиентское подтверждение самого себя**. Сервер до вызова обязан проверить владельца, ревизию, смысл строгих типов/исключений, регион и подтверждение сводки. Наличие строки `confirmed-*` не выполняет эти проверки. Семантика `named_types_only` устанавливается существующим guard, ядро не переинтерпретирует слова и не расширяет список категорий.

День задаётся ISO-датой и окном HH:MM в timezone города. В результате `starts_at`/`ends_at` — минуты от локальной полуночи, деньги — целые копейки на всю компанию. `price.basis=per_person` требует числа участников. Source содержит `provider`, `data_mode`, `fetched_at`, `valid_until`. TTL задаётся серверной политикой; он не доказывает, что провайдер гарантировал актуальность расписания на будущую дату.

## Как выбирается набор

1. Отсеиваются несовместимые рубрики/регионы, запрещённые категории, устаревшие данные, неизвестные координаты/часы работы, неподтверждённые обязательные свойства.
2. Для каждого занятия создаются альтернативы «одно из этих мест». `include_any` — альтернативные типы, а не просьба посетить каждую рубрику.
3. OR-Tools одновременно выбирает места и последовательность. Соблюдаются рабочие интервалы, полный срок посещения, направленные переходы, запас прибытия, порядок занятий и бюджет. Один и тот же объект не заполняет два занятия одного дня.
4. Несколько дневных маршрутов оптимизируются вместе при общем бюджете. Он не копируется на каждый день и не делится поровну молча.
5. Приоритеты по отдельным оптимизационным проходам: покрыть больше занятий → выполнить больше проверенных предпочтений → сократить переезды → использовать рейтинг как слабый критерий → закончить раньше. Сглаживание рейтинга версионировано, но не откалибровано пользовательским исследованием.
6. Отдельная проверка пересчитывает итог: порядок, переходы, часы, сумму и полноту. Нельзя скрыть пропуск занятия или компенсировать нарушение высоким рейтингом.

При дефиците данных возвращаются `LIMITED`/`UNAVAILABLE` с причинами и предложением поменять дату/время или радиус. `AVAILABLE` значит: все занятия помещаются **при переданных фактах и политике**, не гарантия отсутствия очередей/закрытия/пробок в реальности. Оптимальность, если доказана, относится только к переданному пулу.

## Чего пока нельзя обещать

- Сборщик матрицы и повторная проверка маршрута по времени отправления реализованы в `place-planning.ts`; пока проверены только на подготовленных HTTP-ответах. Без подтверждённого ребра проход запрещён; старое ребро от другой точки/даты/режима не подходит.
- Низкоуровневое ядро принимает одиночные walking/driving/cycling с подходящими ребрами. Это **не** объявление всех режимов готовыми в MAX. PT, смешанный транспорт, такси, возрастная применимость, фиксированные события отдельной схемы ещё не реализованы; неподдержанный режим не заменяется пешим.
- Средний чек 2ГИС не верхняя граница. Без подтверждённой единицы расчёта он остаётся `basis=unknown`; при строгом бюджете такие кандидаты исключаются. При явном estimate-режиме всё ещё нужна известная единица. Отсутствие цены не значит «бесплатно».
- График с текстовым исключением остаётся неопределённым. Посещаемость неизвестной шкалы не превращается в «здесь тихо»: сохраняем признак `PRESENT_UNMAPPED`, но не используем для ранжирования.
- Нет достоверных свободнотекстовых fact-resolvers. Сложное требование учитывается только при соответствующем проверенном факте; неизвестное обязательное условие не игнорируется.
- Проверено на синтетических сценариях; это ещё не измерение пользовательского качества, покрытия городов или скорости на больших пулах.

Ограничения вычислений: до 31 дня, 120 занятий на задание, 2000 входных объектов, 120 вариантов solver на день. Прямой solver блокирует превышение; оркестратор до него явно отбирает до четырёх кандидатов на занятие и показывает сокращение в `shortlist.groups`. Это эвристика, не доказательство качества/глобальной оптимальности. Solver имеет общий лимит 3 секунды (до 30 при явной настройке CLI); допустимое решение без доказательства оптимальности маркируется отдельно. JSON-протокол ограничен 8 МБ, TypeScript-процесс — 30 секундами.

## Связь с TypeScript и 2ГИС

- `src/server/place-retrieval.ts`: региональные запросы по `rubric_id`, явные радиус/пагинация/число вызовов, дедупликация внутри одного расчёта, отчёт о частичной выдаче. Не вызывает LLM, не делает автоматических retries и не сохраняет кэш между запросами.
- `src/server/planner-process.ts`: внутренний JSON-вызов настоящего Python-процесса, без передачи API-ключей в его окружение. Пока не публичный HTTP endpoint; для нагрузки потребуется ограниченная очередь/worker deployment.
- `src/server/place-planning.ts`: eligibility → shortlist → dated Routing → solver → проверка выбранных переходов на фактическое отправление. Вход — серверные подтверждённый intent, каталог, политика посещения и явный радиус. Политики, часы сервера, ключи и готовые рёбра не должны приниматься от клиента. Функция не читает `.env`, не вызывает LLM и ничего не сохраняет; тестовый transport передаётся явно.
- Следующая интеграционная задача: связать форму, серверное хранение подтверждённых ревизий и этот внутренний вызов с MAX auth/квотами. Публичного endpoint пока нет; не публикуйте прямой вызов дорогих API без авторизации/лимитов.

### Политика маршрутов `dated-routing.v1`

1. Проверка дат, категорий, времени и режима до внешнего поиска. Для каждого занятия — до 4 допустимых мест (настройка 1–8). Порядок shortlist: подтверждённые предпочтения → географическая близость старта → сглаженный рейтинг. Прямое расстояние никогда не становится временем в пути. Этот выбор ещё нужно оценить на реальных планах.
2. Направленные пары только между совместимыми занятиями, без обратных переходов, нарушающих явный порядок. Исходящие от старта и к явно выбранному финишу; автоматического возвращения в старт нет. Данные Places дедуплицируются в рамках одного запроса, матрицы раздельные по датам.
3. `/routing/7.0.0/global`, batch до 50 пар, `utc` в секундах, `traffic_mode=statistics`, `output=summary`, `save_route=false`. Часовой пояс — город, не компьютер. Ответ-массив сверяется по координатам, не позиции; ошибка пары не даёт нулевое время. Совпавшие координатные пары в одном времени/режиме вызываются один раз.
4. Для машины — три замера внутри окна (начало, середина, последняя минута); пешком/велосипед — начальный. Резерв каждого ребра: `ceil(max(seconds) / 60 * 1.25) + 2 минуты`; перед посещением добавляется отдельно `arrival_buffer_minutes`. Это настраиваемая инженерная гипотеза, **не** статистически гарантированная верхняя граница. Есть `ROUTE_TIME_IS_ESTIMATE`.
5. До расчёта матрицы резервируются две проверки выбранных рёбер. Лимиты по умолчанию: 200 расчётов пар и 30 HTTP запросов Routing, включая проверки. Batch не делает расчёты бесплатными: тарифицируются пары. HTTP retries нет. Перед каждым routing batch проверяется deadline 90 секунд от старта; текущий HTTP завершается/тайм-аутится в пределах тайм-аута клиента. Это не строгий SLA всего запроса, включающего Places/Python.
6. Выбранные рёбра проверяются повторно с выходом из старта в начало окна, затем из места по завершении посещения. Ожидание до открытия возможно после прибытия. Если время выросло, меняются рёбра и разрешён один новый solver-проход; исчезнувшее ребро удаляется. Новый план тоже проверяется. Повторный провал — `ERROR / ROUTE_RECHECK_FAILED`, без старого плана. Отдельно перепроверяются свежесть, порядок, окна и бюджет.
7. Сбой провайдера/неполная матрица отражаются в предупреждениях и счётчиках, не объявляются отсутствием заведений в городе. Меньшее покрытие допустимо только с явным `LIMITED` и недостающими занятиями.

Внутренняя TTL-политика на время одного расчёта: Places 15 минут, Routing 5 минут, без межзапросного кэша/продления свежести старых замеров. Стоимость автомобильной/велосипедной поездки не угадывается: при строгом бюджете требуется политика стоимости, без бюджета `TRANSPORT_COST_UNKNOWN`. PT использует отдельный API и пока не реализован; смешанные режимы не заменяются пешими.

CLI поддерживает служебные операции `--operation prepare-routes` (проекция/shortlist/задание матрицы) и `--operation route-checks` (вход `{job,result}`; независимая проверка и отправления). Обычно их вызывает TypeScript, вручную запускать не нужно.

## Docker

Из корня продукта:

```powershell
docker compose -f compose.planner.yaml run --build --rm planner
```

Изолированное демо без `.env.local` и runtime-сети. Сборке нужен доступ к образам/пакетам. `uv.lock` используется с `--frozen`, runtime непривилегированный, filesystem read-only. Это дополнительный контейнер ядра, **не замена** обязательному работающему сценарию в MAX. Compose config проверен; clean-room сборка/запуск пока не проверены: Docker Engine был недоступен в рабочей среде.

## Технические основания

- [OR-Tools CP-SAT](https://developers.google.com/optimization/cp/cp_solver): готовый solver целочисленных ограничений; FEASIBLE не приравнивается к OPTIMAL.
- [2ГИС Places API](https://docs.2gis.com/en/api/search/places/reference/3.0/items): рубрики/регион, пагинация, обычные и специальные часы работы.
- [2ГИС batch routing](https://docs.2gis.com/en/api/navigation/routing/examples/routing), [контракт Routing](https://docs.2gis.com/en/api/navigation/routing/reference/routing): направленные пары, секунды/координаты, `utc`, статистический трафик. Документация сверена 24.09.2026, live-проверка нового контракта впереди.
- OR-Tools — Apache-2.0; внешние зависимости закреплены в `uv.lock`. Сторонние данные/снимки в поставку этого демо не входят.
